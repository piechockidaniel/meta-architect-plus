# Application management MCP

This is an administrative MCP server for the Architecture decision workspace.
It runs on the developer's machine, separately from the public IWSDK app and its
AI gateway. An MCP host can inspect the project, make conflict-checked source
edits, run fixed tasks, inspect the IWSDK bridge, and manage configured remote
services. It is configurable for more applications later.

The server uses the official
[MCP TypeScript SDK](https://ts.sdk.modelcontextprotocol.io/server). Its incoming
transport is stdio; its upstream clients support
[stdio and Streamable HTTP](https://ts.sdk.modelcontextprotocol.io/client).
There is no public administrative HTTP listener.

## Start and verify

From the project directory:

```powershell
npm install
npm run typecheck
npm run mcp:check
npm run mcp:check -- --upstreams --task check
```

`mcp:check` starts the real server, negotiates MCP, discovers tools/resources/
prompts, inspects the project and reads README. `--upstreams` also discovers each
configured upstream and reads the IWSDK runtime status; it does not recover the
browser. `--task check` runs the fixed project check task through MCP and waits
for its exit state. The task option requires exactly one registered app.

To run the server for an MCP host:

```powershell
npm run mcp:start
```

This is a stdio server: it waits for an MCP client, rather than displaying an
interactive console. JSON-RPC owns stdout. Use a direct Node command in a host
configuration to avoid npm's console messages:

```json
{
  "mcpServers": {
    "architecture-manager": {
      "command": "node",
      "args": [
        "--import",
        "file:///H:/Active%20Solutions/hackathon-meta/devpost-hackathon/node_modules/tsx/dist/loader.mjs",
        "H:/Active Solutions/hackathon-meta/devpost-hackathon/mcp/cli.ts"
      ]
    }
  }
}
```

Copy/adapt [the client example](../config/mcp-client.example.json) to your host's
MCP settings, then reconnect that host. These absolute paths refer to the
current checkout; change them if it moves. For Codex, the equivalent server
entry is:

```toml
[mcp_servers.architecture-manager]
command = "node"
args = ["--import", "file:///H:/Active%20Solutions/hackathon-meta/devpost-hackathon/node_modules/tsx/dist/loader.mjs", "H:/Active Solutions/hackathon-meta/devpost-hackathon/mcp/cli.ts"]
```

The project `.mcp.json` is generated by IWSDK. Keep this custom server entry in
your host settings so IWSDK regeneration does not erase it. This implementation
does not automatically change your host settings.

Generate paths for the current machine with `npm run mcp:client-config`. On
Windows, the loader argument must be a `file:///` URL; the generator handles
spaces and drive letters.

## Operator configuration

The server selects `config/mcp.local.json` when it exists, otherwise
`config/mcp.example.json`. Paths in either file are relative to that file's
directory. An explicit path overrides this selection:

```powershell
Copy-Item config/mcp.example.json config/mcp.local.json -NoClobber
npm run mcp:check -- --config config/mcp.local.json
npm run mcp:start -- --config config/mcp.local.json
```

The local configuration and `.local/` audit history are gitignored. Configuration
is loaded at startup; reconnect the host after changing it. Set
`allowFileWrites: false` to disable source edits. Task commands and arguments are
fixed by the operator; tool callers cannot add shell fragments or arguments.
Task environments inherit only basic OS execution variables plus explicit
environment references, rather than all of the MCP host's secrets.

The supplied app ID is `architecture`. It includes:

- `typecheck`, `check`, `build`;
- `dev-status`, `dev-up`, `dev-down` using the installed IWSDK CLI;
- the installed IWSDK MCP bridge, with 12 explicitly allowlisted tools.

`dev-up` uses `dev up`, preserving a healthy managed server. There is no automatic
restart or browser recovery. Runtime status/targets are read operations. Other
IWSDK tools are conservatively classified as `local-write` because a managed
command can recover a browser or create an artifact. Use the plan workflow for
those calls and inspect IWSDK's returned envelope. A successful transport call
alone does not prove an active immersive session or a working headset.

## Tool catalogue

| Tools | Purpose |
| --- | --- |
| `app_list`, `app_inspect` | Registered capabilities, package/IWSDK config, build presence, running jobs |
| `app_ai_status` | Enabled/provider/model/credential-present/call-limit status; no key or inference call |
| `project_files`, `project_read`, `project_search` | Confined text inspection, line numbers and SHA-256 |
| `project_write` | Full text replacement or new file, guarded by current SHA-256 |
| `project_git_status` | Working-tree status without staging or committing |
| `task_list`, `task_start` | Fixed configured commands; returns a job ID |
| `job_list`, `job_get`, `job_cancel` | Job progress, bounded redacted output, cancellation |
| `remote_http_read` | A named configured GET operation |
| `upstream_tools`, `upstream_read`, `upstream_resource` | Allowlisted upstream MCP schemas, read calls and exact resource URIs |
| `remote_prepare`, `remote_apply` | Review and execute a one-use configured write |
| `audit_tail` | Recent action/outcome metadata |

The `app-manager://apps` resource provides inventory. The `maintain_app` prompt
provides the inspection/change/check workflow.

## Specialist agent

The project includes a Codex role,
[`architecture_app_manager`](../.codex/agents/architecture_app_manager.toml),
and its [operating reference](agents/architecture-app-manager.md). It discovers
the current tool contracts, preserves user edits, follows jobs to completion,
and verifies local/remote changes before reporting success. The role includes
the MCP connection and inherits the parent session's model and permissions.

In a new/reloaded Codex session rooted at this project, ask:

> Use architecture_app_manager to inspect the app and report current runtime
> and check status. Keep this task read-only.

See the operating reference for maintenance examples, plan/error handling and
host setup. Creating the definition does not start an agent or a paid model run.

## Typical local workflow

1. Call `app_inspect` and `project_git_status` for `architecture`.
2. Read README and applicable AGENTS instructions with `project_read`.
3. Inspect the affected source. Retain the returned `sha256`.
4. Use `project_write` with that exact hash and the intended replacement. For a
   new file use `expectedSha256: null`; its parent must exist.
5. Start `typecheck` or `check` with `task_start`. Poll `job_get` until it finishes.
6. Start `build` when the checks pass. Report the actual exit state and output.

Hashes reject stale edits. New files use an atomic no-clobber create. Existing
files are rechecked before replacement; this is optimistic conflict detection,
not an OS-level transaction against a hostile concurrent process. Redacted files
cannot be rewritten through MCP. There are no file-delete, arbitrary-shell,
git-reset, commit, merge or deployment commands in the default configuration.

## Add a remote HTTP service

Add a named endpoint under `apps.architecture.endpoints` in the local config:

```json
{
  "production": {
    "description": "App operations API",
    "url": "https://ops.example.com",
    "headersEnv": { "Authorization": "APP_OPS_AUTHORIZATION" },
    "timeoutMs": 15000,
    "operations": {
      "health": { "description": "Read app health", "method": "GET", "path": "/health", "effect": "read" },
      "restart": { "description": "Restart this app", "method": "POST", "path": "/apps/architecture/restart", "effect": "remote-write" }
    }
  }
}
```

The referenced environment value supplies the **whole** header, for example
`Bearer <token>`. Set it in the environment that launches the MCP host; do not put
credentials in config, tool arguments or URLs. HTTPS is required except for
loopback development HTTP. Operation paths are absolute paths within the
configured origin. Redirects are rejected.

The existing app does not expose a `/health` or restart endpoint. This example
requires your actual operations API; it is not an assertion that a deployment
already exists. No remote host or credential has been configured by this work.

## Add a remote MCP server

Add an upstream under `apps.architecture.upstreams`:

```json
{
  "deployment": {
    "description": "Deployment provider MCP",
    "transport": "http",
    "url": "https://ops.example.com/mcp",
    "headersEnv": { "Authorization": "DEPLOYMENT_MCP_AUTHORIZATION" },
    "timeoutMs": 30000,
    "tools": {
      "deployment_status": { "effect": "read" },
      "restart_app": { "effect": "remote-write" }
    },
    "resources": ["deployment://architecture/status"]
  }
}
```

Tool names and resource URIs above are placeholders. Use the provider's actual
contract. `upstream_tools` returns discovered schemas only for allowlisted names,
and reports configured names absent from the server. The operator assigns effects
instead of trusting upstream annotations to authorize writes. Resource access
requires an exact configured URI. Connections are opened per request and closed
afterward; cached provider sessions and automatic write retries are not used.

For local upstreams use `transport: "stdio"`, `command`, `args`, optional `cwd`,
and `env` mapping child variable names to host environment variable names.
Prefer `command: "node"` with a JS entrypoint for portable Windows operation.
Shell script executables are not launched implicitly. OAuth login/refresh and
legacy SSE upstreams are not implemented; use supported header credentials or a
local provider MCP process that owns its authentication.

For a server managed over SSH, a fixed task is another supported option. For
example, configure `command: "ssh"` with fixed arguments
`["-o", "BatchMode=yes", "operator@your-host", "systemctl", "is-active", "your-app.service"]`
and effect `read`. A fixed restart command belongs in a separate task with
effect `remote-write`, executed through a plan. Use your actual host, service
and existing SSH authentication; these examples do not provision access.

## Write workflow and uncertain outcomes

Prepare a remote write:

```json
{
  "action": {
    "kind": "http",
    "appId": "architecture",
    "endpointId": "production",
    "operationId": "restart",
    "body": { "reason": "Apply reviewed maintenance" }
  }
}
```

Call `remote_prepare`, review its exact target and arguments, then call
`remote_apply` with the returned `planId` and `digest`. A plan expires after five
minutes and can be consumed once. The same path supports `kind: "mcp"` with
`upstreamId`, `toolName`, `arguments`, and `kind: "task"` with `taskId` for a fixed
task classified `remote-write`.

The plan is a review mechanism, not user authentication or proof of human
approval: an MCP client with access to both tools can prepare and apply it. The
host must enforce the user's authorization policy. A timeout, dropped connection
or error from a dispatched write can mean it partially executed. The tool
reports `outcome_unknown`; check the target before attempting another write.
An HTTP 2xx means the API accepted/completed the request according to its own
contract, not that the deployed app has passed a subsequent health check.

## Boundaries and evidence

- Trusted local operator: configuration can launch programs with the local
  user's privileges. This is not a multi-tenant sandbox. Run it in a trusted host.
- Text tools deny secrets/runtime/dependency directories, secret file names,
  operator configuration, path escape, alternate data streams and symbolic links.
  Redaction is best effort; avoid storing credentials in source or tool output.
- Jobs per MCP process: at most four concurrent tasks, one per app/group, 100
  retained jobs, 65,536-character output tail, configured timeout up to five minutes. Shutdown cancels
  owned jobs. Managed IWSDK servers started by its lifecycle command are owned
  by IWSDK; use `dev-down` to stop them.
- Remote bodies/results: bounded payloads; HTTP responses capped at 128 KiB;
  upstream stdio messages capped at 1 MB. Upstream content is marked untrusted.
- Audit: action/app/target/job/outcome metadata only, 5 MB current file and one
  rotated predecessor. Audit starts must succeed before actions; completion
  logging failures are reported without pretending a successful write failed.
- MCP itself requires no AI provider or inference budget. A connected MCP host
  may use a model under its own billing. Provider tools can have their own costs;
  only register operations you intend to make available.

Automated tests exercise the MCP protocol, path confinement, optimistic edits,
job lifecycle, loopback HTTP operations, stdio upstreams, Streamable HTTP
upstreams and one-use writes. The installed IWSDK bridge has also been discovered
and queried through this server. Actual remote deployments and Quest hardware
actions require configured targets and separate validation.

Remaining operator choices: which remote deployment/API to register, which
operations to expose, credential environment names, and which MCP host should
load the server. None prevents using the local project tools now.
